1. Project map

The simulator is organised around one rule: screen code asks for input, while the model classes perform and enforce ATM operations.

main.py └── creates ATM ────────┐ v ui.py (CLI) ────────► ATM (models.py) ◄──────── ATM_Website/server.py │ │ ├── Account hierarchy └── HTTP + JSON API ├── NoteDispenser └── persistence ──► storage.py ├── SHA-256 PIN hashes ├── JSON load/save ├── receipts └── statistics
File Responsibility
main.py Application entry point. Creates the ATM and starts the command-line interface.
models.py Core classes and business rules: accounts, inheritance, cash, login, transactions and admin operations.
storage.py Hashing, JSON persistence, text receipts and aggregate statistics.
ui.py Terminal menus, input prompts, tables and mini-statements.
tests.py Assert-based tests for core account and ATM behaviour.
ATM_Website/server.py Browser adapter. Converts HTTP/API requests into calls to the same core ATM object.
Important: The CLI and website share models.py. They do not duplicate the banking rules.

What ATM.__init__ does

  1. Calls load_data() from storage.py.
  2. If the file is missing or corrupted, creates default accounts and a new note dispenser.
  3. If a saved file exists, reconstructs account subclasses and ATM notes from dictionaries.
  4. Stores the active customer in current_account.

Web version

ATM_Website/server.py creates one ATMWebApp, which owns an ATM object and a threading.Lock. The lock prevents simultaneous HTTP operations from changing state at the same time.

3. Account inheritance map

Account ├── balance, owner, PIN hash, limits ├── deposit(), withdraw(), transfer() ├── record_transaction(), mini_statement() ├── change_pin(), verify_pin() │ ├── SavingsAccount(Account) │ ├── 3% interest │ ├── monthly withdrawal limit (4) │ └── apply_interest() │ └── CurrentAccount(Account) ├── overdraft limit (10,000) └── minimum balance = -overdraft limit
Class minimum_allowed_balance Extra rule
Account / Standard min_balance (default 1,000) None beyond standard limits
SavingsAccount Inherits 1,000 minimum 4 withdrawals per month; 3% interest
CurrentAccount Negative overdraft limit May go down to −10,000
Why inheritance? Savings and Current accounts share deposit, PIN, transfer and persistence logic, but override only the rules that differ.

4. Login and PIN security flow

Account number
→
Find account
→
Hash entered PIN
→
Compare stored hash

ATM.login()

  1. Look up the account number in self.accounts.
  2. Reject it immediately if is_blocked is true.
  3. Call account.verify_pin(pin).
  4. For a valid PIN: reset failed attempts and set current_account.
  5. For an invalid PIN: increase failed_attempts.
  6. At three failures: set is_blocked = True.
  7. Save account state after success or failure.
Security detail: Plain-text PINs are never saved. storage.hash_pin() uses SHA-256. It is also salted? No—it is a deterministic SHA-256 hash with no salt in this project.

Admin login

verify_admin_pin() hashes the entered admin PIN and compares it with admin_pin_hash. The default is 0000.

5. Withdrawal flow — step by step

ATM.withdraw(amount) │ ├─ 1. Is a customer logged in? ├─ 2. Account.can_withdraw(amount) │ ├─ amount > 0 │ ├─ amount ≤ per-transaction limit │ ├─ daily withdrawal + amount ≤ daily limit │ └─ remaining balance ≥ minimum allowed balance │ ├─ 3. SavingsAccount can-withdraw also checks monthly count ├─ 4. NoteDispenser.calculate_notes(amount) ├─ 5. Dispense and deduct ATM notes ├─ 6. Account.withdraw() deducts balance and records transaction ├─ 7. save() persists JSON └─ 8. build and save a text receipt

Example: withdraw 5,000 from Ada

Check Result
Logged in Yes — Ada is current_account
Per-transaction limit 5,000 ≤ 20,000
Daily limit Daily total plus 5,000 is within 50,000
Minimum balance Balance must remain at least 1,000
Monthly Savings limit Withdrawal count remains below 4
Notes {1000: 5} can form the amount
Only after every check succeeds does the code update both the account balance and the ATM note inventory.

6. The non-greedy note algorithm

NoteDispenser.calculate_notes() must find an exact combination, not simply take the largest notes first.

Memoised bounded search

  1. Reject non-positive or non-whole amounts.
  2. Reject amounts larger than total ATM cash.
  3. Sort denominations from largest to smallest.
  4. Try the maximum possible count of the largest denomination.
  5. Decrease that count and call the next denomination recursively.
  6. Store failed (denomination_index, remaining_amount) states to avoid repeated work.
Tricky example: with 500 × 1 and 200 × 3, request 600.
3 × 200 = 600 succeeds. A simple greedy 500-first plan would fail; this recursive search finds the valid plan.

Dispense ordering

calculate_notes()
→
Return note plan
→
Subtract notes
→
Return plan
Transaction consistency note: In ATM.withdraw(), notes are currently dispensed before Account.withdraw(). The account withdrawal should normally already pass the account-level check, but a race or unexpected failure could temporarily leave notes changed without a balance update.

7. Deposit, transfer and interest

Deposit

Account.deposit()
→
Add balance
→
Record transaction
→
save() + receipt

Transfer

  1. Confirm a customer is logged in.
  2. Find the recipient account.
  3. Reject missing recipients and transfers to the sender's own account.
  4. Check the sender's minimum balance rule.
  5. Subtract from sender and add to recipient.
  6. Record transfer_out and transfer_in entries.
  7. Save both account states and create a receipt for the sender.

Savings interest

interest = round(balance × 0.03, 2). The interest is then added to the balance and recorded as an interest transaction. It is unavailable for Standard or Current accounts.

8. Data persistence — JSON and receipts

storage.py

  • load_data(filepath) validates existence, readability, JSON syntax and the accounts key.
  • save_data() writes the admin PIN hash, note inventory and all account dictionaries.
  • save_receipt() creates a timestamped text file in the receipt directory.
  • compute_statistics() scans transaction histories.

JSON account structure

{ "admin_pin_hash": "...", "notes": { "1000": 60, "500": 40, ... }, "accounts": { "1001": { "account_class": "Savings", "owner": "Ada Obi", "pin_hash": "...", "balance": 50000.0, "transactions": [...] } } }

Reconstruction

account_from_dict() checks account_class and calls the correct subclass's from_dict(). This restores Savings, Current or Standard behaviour after restarting.

The JSON file holds state. ATM.save() is called after login attempts and successful or persisted operations.

Method result pattern

Operation Typical return
Login / PIN / admin (ok: bool, message: str)
Account deposit / withdrawal / transfer (ok: bool, message: str, info: dict | None)
Can-withdraw validation (ok: bool, message: str)

The UI does not decide whether a transaction is legal. It sends values to ATM, displays the returned message, and prints extra information from info.

Mini-statements

mini_statement(count=5) returns self.transactions[-count:]. This means the newest entries are obtained from the end of the list, while transaction entries are ordered oldest to newest.

Response pattern

The web wrapper returns JSON such as {"ok": true, "message": "...", "account": {...}, "info": {...}}. The browser uses ok to show success/error and refreshes state after the operation.

11. Statistics

storage.compute_statistics(accounts) loops through every account and every transaction, then calculates:

  • total_transactions
  • counts_by_type, such as deposit or withdrawal
  • largest_deposit with amount, account number and timestamp
  • largest_withdrawal with amount, account number and timestamp
  • busiest_hour based on timestamp hour

Example timestamp parsing

datetime.strptime(timestamp, "%Y-%m-%d %H:%M:%S") extracts the hour. Malformed timestamps are ignored safely.
